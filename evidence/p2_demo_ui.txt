## IMPORTANT operational finding (not a code defect — affects demo-day reliability)
While testing Step 2/3 back-to-back, several POSTed ratings took 40s-60s+ to reach
"applied" instead of the usual ~15-25s, causing the UI's 30s poll timeout to fire even
though the pipeline was healthy and had not actually stopped. Root-caused as follows:

1. A leftover background loop from earlier in this session (an `until` shell loop with a
   condition that never became true) was silently re-running a one-off Spark job every
   ~5-10 seconds, indefinitely, for hours. This left 328 zombie ("<defunct>") processes in
   the `spark` container and was consuming CPU concurrently with the real streaming
   pipeline. Fixed by stopping the loop and `docker compose restart spark`.
2. Independent of (1): `raw_events` (the Q1 Kafka->parquet file sink) accumulates a new
   small file on every 5s trigger for the life of the pipeline process, whether or not
   there was new data. After several hours of a running pipeline (accumulated across this
   whole session's testing), the "parsed" stream's file-source listing step
   (`FileStreamSource: Listed N file(s)`) measurably slows down as N grows — observed
   batches taking 25-58s against the 5s trigger interval on this Windows/Docker
   Desktop/WSL2 setup, even with (1) fixed and zero concurrent jobs running.

Neither is a bug in this change's code — the API and UI behave exactly per spec in both
cases (503/pending/timeout-hint all fire correctly). It is a characteristic of a
long-running Structured Streaming file-sink demo environment on Windows.
Recommendation for demo day (added to docs/TESTING_GUIDE.md): shortly before presenting,
`docker compose restart spark` and relaunch `streaming.pipeline` fresh so `raw_events` file
count / any lingering diagnostic processes don't carry over from rehearsal, and avoid
running extra `docker compose exec spark ...` one-off commands while the live demo is in
progress.

## CORRECTION (2026-10-01) — cause of the slow batches
Point 2 above blames "raw_events accumulates small files; listing slows down as N grows". Later
measurements do not support it (31 files, 260 KB, listing 2-4 s; latency better than on 29/09 with
fewer files). Point 1 (runaway loop, 328 zombies, concurrent Spark jobs) stands. The real structure
of the delay (two chained queries x ~10 s batches) and the fix for the other problem found here
(streaming not restarting by itself) are in evidence/p2_streaming_latency.txt.
