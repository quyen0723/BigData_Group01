=== 2. B1 - HANDOFF WINDOW BOUNDED BY COMMITTED EVENTS (design D-1) ===
BEFORE (code reading, not executed): retrain_trigger.py queried `ingestedAt > watermark` with no upper bound (old line 51), took
`now` at old line 97 and wrote `watermark = now` at old line 117. An event applied between the query and the watermark write has
ingestedAt in (query time, now): it is in neither this package nor the next one. The Spark write sits in that gap.
NOTE ON THE REVIEW: it says maxEventTimestamp is "computed but unused". It is used (manifest + checksum) and it is the rating's own
timestamp, not ingestedAt, so it must not become the watermark. Review also proposes watermark = max(ingestedAt of pending); that
still loses the rest of a batch whose insert_many is half done (one ingestedAt per batch), hence the lastRunAt bound.

AFTER: window = (watermark, lastRunAt of the last committed batch]; new watermark = that bound; manifest windowEnd = that bound.
unit tests: tests/unit/test_handoff_window.py 8 passed (full suite 132 passed)

=== 3. B3 - BATCH GUARD BOUND TO THE CHECKPOINT (design D-2) ===
BEFORE (old code, reproduced on the running stack, task 3.1):
  1. docker compose stop streaming; mv movielens32m/stream/checkpoints/valid valid.bak  (Q2 checkpoint lost, Mongo untouched:
     pipeline_state.ratings_stream.lastBatchId = 69); docker compose start streaming.
  2. Spark created a new checkpoint (metadata id 89fe5d54-... -> c044a59b-...) and numbered batches from 0 again. Log:
       serve_batch[0]: already committed (last=69), skipping     <- the whole replay of raw_events, harmless (already in the ledger)
  3. POST /ratings {userId 999100001, movieId 296, rating 4.0, eventId review-fix-b3-before} -> 202 accepted.
     GET /ratings/review-fix-b3-before polled for 112 s: status "pending" every time (batchId null, ingestedAt null). Log:
       serve_batch[1]: already committed (last=69), skipping     <- the new rating is dropped, the log looks healthy
     => the guard compares Spark's per-checkpoint counter with Mongo's durable lastBatchId; every batch with id <= 69 is skipped,
        i.e. about the next 69 batches that carry data. (The review says "permanently"; it is bounded, but the effect for a user is
        the same: 202, then "pending" forever, nothing in the logs says that data was dropped.)
  The rating review-fix-b3-before is lost by this experiment (it is a synthetic rating of user 999100001; it is not in the ledger).
  WORSE THAN THE REVIEW SAYS (found while testing the fix, same experiment): the old guard `return`s without touching batch_df. Q2
  has a state store (dropDuplicatesWithinWatermark) that only advances when the batch plan runs, so the skipped batches 0 and 1 left
  no state files but Spark still committed their offsets. Checkpoint left behind by the repro:
       offsets 0,1,2   commits 0,1   state/0/0/ = only "_metadata" (no N.delta)
  The next batch that was actually processed (batch 2, after I restarted the container on the new code) failed with
       java.io.FileNotFoundException: .../checkpoints/valid/state/0/0/1.delta does not exist
  Query c044a59b terminated with error, container restarted 3 times and kept crash-looping (restart: unless-stopped).
  So with the old guard a lost checkpoint is not only "ratings dropped for ~69 batches": it ends in a corrupt checkpoint and a crash loop.
  Fix therefore has two parts: (1) skip only when the checkpoint identity matches, (2) read the batch before deciding to skip.
