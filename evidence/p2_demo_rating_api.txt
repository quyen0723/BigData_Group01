## Test 1 — valid rating: 202, published to Kafka, applied after streaming commits
POST /ratings {"userId": 500001, "movieId": 296, "rating": 4.5}
  -> 202 {"eventId":"c51b5709-e8c5-485d-8af8-e0b543678ae2","status":"accepted"}
GET /ratings/c51b5709-... immediately after
  -> 200 {"status":"pending","batchId":null,"ingestedAt":null}
Confirmed on the raw side (spark container, read raw_events parquet):
  raw_events matching eventId: 1 row, value = {"eventId":"c51b5709-...","userId":500001,
    "movieId":296,"rating":4.5,"timestamp":1790672710,"source":"demo"}
  quarantine matching eventId: 0 rows (not rejected)
Confirmed applied (mongo, direct read):
  rating_events._id=c51b5709-... -> {batchId:24, ingestedAt: 2026-09-29T09:07:27.974Z}
GET /ratings/c51b5709-... after the pipeline committed
  -> 200 {"status":"applied","batchId":24,"ingestedAt":"2026-09-29T09:07:27.974000"}
PASS: 202 means durably queued, not applied; status transitions pending -> applied once
      serve_batch's ledger insert lands (pipeline.py: ledger write happens AFTER effects).
NOTE: this run's applied latency was ~40-60s wall clock (poll loop still "pending" at 30s of
      2s-interval polling), likely because a leftover check process from earlier in the
      session (PID 46618, a one-off `spark.read.parquet(...).count()` from the invalid-event
      test) was competing for the single-node Spark container's CPU. A second POST run below
      (clean container, no contention) applied in ~20s. Documented as a real observed range,
      not a bug — see docs/TESTING_GUIDE.md demo section for the presenter-facing framing.

## Test 2 — 422 validation, no Kafka publish (checked via server-side rejection, all before produce())
POST /ratings {"userId": 1, "movieId": 296, "rating": 7.0}
  -> 422 {"detail":"rating must be one of [0.5, 1.0, 1.5, 2.0, 2.5, 3.0, 3.5, 4.0, 4.5, 5.0]"}
POST /ratings {"userId": 1, "movieId": 999999999, "rating": 4.0}
  -> 422 {"detail":"unknown movieId 999999999"}
POST /ratings {"userId": 0, "movieId": 296, "rating": 4.0}
  -> 422 {"detail":"userId must be a positive integer"}
POST /ratings {"userId": 1, "movieId": 296, "rating": 4.0, "eventId": "<65 chars>"}
  -> 422 {"detail":"eventId must be 1-64 characters when supplied"}
GET /ratings/does-not-exist-at-all (never posted)
  -> 200 {"status":"pending","batchId":null,"ingestedAt":null}
PASS: all 4 validation rules reject with 422; unknown eventId reads as pending, not 404
      (matches spec: absence in rating_events means "not applied yet", not "unknown").

## Test 3 — Kafka outage: POST 503, GET /recommendations unaffected
docker compose stop kafka
POST /ratings {"userId": 500001, "movieId": 296, "rating": 3.0}
  -> 503 {"detail":"kafka delivery timed out"}
  (producer.flush(10s) returned >0 messages still in-flight; librdkafka had already cached
   broker metadata from the earlier successful produce, so it queued and timed out rather
   than failing fast — matches design.md D-6's flush-timeout branch, not the delivery-error
   branch, but both map to the same 503 outcome)
GET /recommendations/1
  -> 200 {"userId":1,"tier":"enough_history","strategy":"ALS+CONTENT", ... 10 recommendations}
PASS: read path has no dependency on the Kafka producer/connection at all.
docker compose start kafka -> healthy after ~45s (KRaft controller warm-up, consistent with
  configs/streaming.yaml's note about broker startup flakiness)

## Test 4 — pipeline self-heals after Kafka comes back, without restarting the spark container
streaming.pipeline process (PID 22) never died during the outage (`ps aux` unchanged before/after).
POST /ratings {"userId": 500001, "movieId": 318, "rating": 5.0}
  -> 202 {"eventId":"e8bc57a3-f9c0-448b-a7a2-28a9446f155b","status":"accepted"}
GET /ratings/e8bc57a3-... polled every 2s
  -> applied at attempt 10 (~20s): {"status":"applied","batchId":28,
     "ingestedAt":"2026-09-29T09:11:36.865000"}
PASS: Spark's Kafka source reconnects on its own; no manual pipeline restart needed after a
      broker outage recovers.
