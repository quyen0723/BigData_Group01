=== 4. INDEPENDENT REVIEW AND FIXES (task 6.3, section 8 of tasks.md) ===
Review (read-only, a separate agent, 24 files): REQUEST CHANGES. 0 critical, 3 high, 8 medium, 9 low, 5 documentation drifts. The spec-compliance pass found two real contract deviations (nullability of trainRatings/newRatings, and the
blocking re-read written in the spec while the code refreshes in the background). Every point was checked in the code before it was fixed. PR #3 had been merged by the time the fixes were ready, so they travel in a second PR.

Measured BEFORE the fix, on the real stack (laptop, other containers running; /movies is demo-only):
  /movies?sort=wr&size=50   0.58-1.61 s per request      /movies?sort=ratings 0.26-0.29 s      /movies?sort=title 0.29-0.32 s      /movies?q=pulp 0.07-0.11 s (first 0.46 s)
  /recommendations/1?k=10   0.03-0.07 s idle, but 0.84-1.83 s while four clients looped /movies?sort=wr;   /health 0.11-0.40 s under the same load.
Cause: every request sorted the whole 87,585-movie catalog (the "sort everything" figure of section 2 was 130-250 ms on a quiet machine) and held a worker and the GIL while doing it.

High
  1. OrderCache (src/serving/catalog.py): the whole catalog in each (sort, direction) is computed once and kept while the entries, the baseline and the ledger deltas are the same objects; a search filters that order and takes
     its page (filtering keeps the order). One order is built at a time; the number kept is bounded (16). LivePopularity returns the same deltas object while the ledger content is unchanged.
  2. LivePopularity.snapshot() had no non-blocking path: a /movies request could queue a cold /recommendations behind a ledger aggregation. It now has the TTL cache and the "a reader with a recent answer does not wait" path of
     get(), and serves the previous result (up to 60 s) when a refresh fails.
  3. CatalogCache leaked its lock when the refresh thread could not start (RuntimeError "can't start new thread"): the catalog never refreshed again and invalidate() (POST/DELETE /movies) hung. The lock is released and the
     previous copy is served.
Medium (fixed)
  - invalidate() no longer waits for a read in progress (generation counter; a read that began before it is not published). Measured by the review: it could hold POST /movies for the whole 2.3 s read.
  - search() refuses page < 1 and size < 1 (a negative page returned rows from the end of the list; not reachable through the API, where FastAPI's ge=1 already answers 422: hardening for other callers).
  - Admin table: the page returns to 1 while rendering, not in an effect (the effect sent the new filter with the old page, then again with page 1); an error after a first successful load is shown (it was hidden because the
    old data was kept); a 422 for avg/wr falls back to the rating count; the heading and the pager use one page number; the search text is trimmed before the pause.
  - User search: a one-letter title with a genre selected says it is not used ("Tên phim cần ít nhất 2 ký tự nên chưa được dùng để lọc"), where the box looked broken. A 4xx answer is no longer retried; the search list is not
    reloaded page by page on every window focus; the result list is memoised.
  - trainRatings and newRatings are counts and are 0 when there are none (spec and design said null, the code and a test said 0): the spec and the design were changed, since "0 ratings" is more exact than "unknown".
Documentation: spec (statistics, cache, new requirement "A search does not sort the catalog"), design D-1/D-3/D-5 and the risks, tasks 3.1/3.2 and section 8.

AFTER the fix (api image rebuilt, same machine):

=== 5. SECOND INDEPENDENT REVIEW (of the fix in section 4) ===
Result: REQUEST CHANGES, "not for correctness (it could not break it) but for memory": 1 high, 3 medium, 5 low, 6 documentation claims. PR #4 (section 4) had been merged by the time it came back, so these fixes are a third PR.
The reviewer ran the suites (pytest 365, Vitest 217, build PASS) and confirmed that filtering an ordered list gives the old filter-then-sort result, that identity comparison cannot be fooled by id reuse, and that it could not build a
get()/invalidate()/refresh interleaving that returns None, serves data older than a completed invalidate(), starves, or leaves the lock held.

High (reproduced here): OrderCache pinned every order to the entries list it was built from, and every 30 s refresh built a new list of 87,585 new CatalogEntry objects even when the catalog was identical, so each key left
alone kept its own generation alive. One generation is about 43 MB (tracemalloc). Eight keys over eight refreshes, measured with the same kind of script: 85, 128, 171, 214, 257, 300, 343, 386 MB held; with 16 keys about 690 MB, in a
container with no memory limit.
Fix: (1) a refresh that reads an identical catalog keeps the existing list object (nothing new is allocated and the sorted orders stay valid: this is also what makes "sorted once" true across the 30 s boundary, where before every
order was rebuilt every 30 s); (2) CatalogCache clears the orders when it publishes a different list, and storing an order drops any order built from another list; (3) at the bound the oldest order goes, not all of them.
Measured after the fix: identical catalog 43.0 MB at the first refresh and 47.9 MB after eight (0.7 MB per new order); a catalog whose content changes at every refresh stays at 42.3 MB. (One run of the identical-catalog script printed 84.7
MB at the eighth refresh; two reruns printed 47.9 MB both times, so it was a one-off reading; the changing-catalog script first printed 84.6 MB because its own loop variable still held the previous list, which is fixed in the script.)

Medium / low, all fixed except where said
  - The "cached_order" mode of the brute-force test never hit the cache for four of its five cases (a new {} was passed at every call): the empty deltas are now one object and the test counts the builds (5 for 5 different sorts).
  - OrderCache serialises builds, so a request for another order can wait for the one in progress (it was documented as "only the same order waits"): the docstring, design and spec now say what the code does. Serial builds are deliberate:
    concurrent ones are what slowed /recommendations.
  - The test named "a cached snapshot without a baseline is served while the lock is held" only covered the TTL fast path: a cached "no statistics" answer is served inside its TTL, and after it the reader waits for the lock (a cached
    statistics answer does not). Renamed, docstring and section 4 corrected.
  - _start_refresh assigned the worker after start(): now before, and reset to None when the thread cannot start; wait() right after a failed start is tested.
  - At the bound the whole order cache was cleared: now the oldest order goes (a 53-key test, since 48 = 3 x 16 made the first version of that test pass by coincidence: found by the mutation check).
  - The 422 fallback of the admin table kept the direction chosen for the average (ascending = the least rated first): it goes back to the default direction. The heading and the pager both show the page of the rows on screen, not the
    requested one (a slow second page is tested).

Documentation claims the reviewer showed to be wrong, corrected: "a few tens of MB" (43 MB per generation, 0.7 MB per order); "then 0.013-0.020 s" (section 4; over 80 s and two 30 s refreshes the final code gives a median of 22 ms and a smallest of 11 ms, with 1 round of 52 above 0.1 s (0.119 s, at the refresh); an earlier run of the same script on a busier machine, before the last change, gave a median of 38 ms and
5 of 51 rounds taking 0.11-0.58 s, at 31 s, 36 s, 47 s, 64 s and 66 s: the background thread that rebuilds the 87k entries competes for the GIL; sort=ratings page 2: median 17 ms, one round of 0.117 s on the final code); "sorting takes
0.1-1 s" (alone, over 87,585 entries: title 25 ms, ratings 55 ms, wr 205 ms; through the API 0.3-1.6 s because of Mongo, serialisation and GIL contention); "the catalog is sorted once" across a 30 s boundary (true only now);
"search() refuses page < 1" listed as a fix (not reachable through the API, FastAPI answers 422: module hardening only).

Tests: pytest 367 (365 before: +2 net), Vitest 219. Mutation checks on these fixes: backend 5 of 5 caught (older generations not dropped, a replaced list for an identical catalog, the whole cache cleared at the bound, an unstarted worker left to
join, the newest order evicted; the "cleared at the bound" mutant survived until the 53-key test), frontend 3 of 3 (direction kept on fallback, heading and pager using the requested page).
