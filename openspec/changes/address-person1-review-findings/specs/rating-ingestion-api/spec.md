## ADDED Requirements

### Requirement: Delivery timeout means unknown outcome
When publishing to Kafka does not complete within `api.produce_timeout_seconds`, the API SHALL respond HTTP 503 and the response detail SHALL state that the rating may still be delivered and that a retry must reuse the same `eventId`. The API SHALL keep `eventId` optional; an `eventId` generated by the server SHALL NOT be presented as an idempotency key for retries. A client that retries after a 503 with the same `eventId` SHALL result in a single ledger document for that `eventId`.

#### Scenario: Timeout response text
- **WHEN** the producer flush returns with messages still queued
- **THEN** the API returns 503 and the detail tells the client the outcome is unknown and to retry with the same `eventId`

#### Scenario: Retry after a late delivery
- **WHEN** a client posts with `eventId` "E", receives 503 on timeout, the broker later accepts the first message, and the client retries with "E"
- **THEN** after the pipeline processes both messages the ledger holds one document for "E" and the user's history reflects the rating once

### Requirement: Reference client reuses the event id on retry
The user app SHALL reuse the same `eventId` when it resubmits the same `(userId, movieId, rating)` after any outcome other than 202 or 422, and SHALL discard every `eventId` it retained for that `(userId, movieId)` after a 202 or a 422, whatever the star value, so an id left over from another value can never be reused for a later rating.

#### Scenario: Retry after a server error
- **WHEN** a rating submission returns 503 and the user submits the same rating again
- **THEN** the second request carries the same `eventId` as the first

#### Scenario: Id left over at another star value
- **WHEN** a 4-star submission returned 503, the user then submitted 5 stars for the same movie and got 202, and later submits 4 stars again
- **THEN** the 4-star request carries a new `eventId`, not the one from the failed attempt

#### Scenario: New rating after success
- **WHEN** a rating was accepted with 202 and the user later submits another rating for the same movie
- **THEN** the new request carries a new `eventId`
